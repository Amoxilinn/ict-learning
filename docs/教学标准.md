# 零基础网络工程教程 · 统一教学标准

本文件是 94 章、322 个知识点的共同写作标准。所有章节必须按同一套教学逻辑写作，但不允许套用同一个小标题模板。判断标准只有一条：**一个没有网络基础的学生，能否沿着文字自己把因果关系想明白，并能把同一套理解迁移到新场景。**

## 一、目标读者与最终深度

- 起点：会使用电脑和手机，知道“上网”，但没有系统学过网络。
- 终点：能解释常见协议为什么这样设计、报文如何逐跳变化、故障从哪一层开始查；达到华为 ICT 大赛省资格赛/省赛所要求的原理深度。
- 不假设读者已经知道任何缩写、设备角色或命令视图。首次出现的术语必须先给出“它解决什么问题”的通俗说明，再给出正式名称与定义。
- 不把读者当外行哄劝。语言通俗，但技术结论、条件、方向和边界必须准确。

## 二、每个知识点的教学逻辑

写作顺序遵循认知规律，而不是固定栏目：

1. **为什么需要**：先给一个具体场景、矛盾或问题。让读者感到“没有这个机制会怎样”。
2. **直观理解**：用已有知识搭桥，说明核心想法。可以用类比，但类比必须能经受技术推敲，不能为了生动牺牲准确性。
3. **工作过程**：按时间或因果顺序说明“先发生什么、看到什么、接下来做什么”。适合用编号步骤的地方才用步骤。
4. **技术原理**：解释为什么这样设计、关键字段/表项/状态如何配合、常见条件是什么。
5. **实践应用**：说明在真实网络或实验里如何观察、验证、配置；指出最容易出现的误解。

这五步是**写作检查顺序**，不是页面上的五个固定标题。页面小标题应写成自然的问题或判断句，例如“交换机先看谁”“为什么第一次会泛洪”“标签在哪一段被去掉”。不要机械使用“为什么需要”“直观理解”“技术原理”作为每个知识点的小标题。

### 层次划分

每个知识点标注一个层次，写入 `level`：

- `core`（基础必学）：零基础必须掌握的主干。解释完整，不依赖后面才出现的概念；是默认阅读路径。
- `advanced`（进阶理解）：需要先掌握本章基础，解释条件、对比、设计取舍或组合场景。
- `detail`（技术细节）：报文位段、定时器、特殊型号行为、异常分支、复杂排障等。允许放在本章后部，允许读者第二遍再读。

一个知识点只承担一个主问题。不要把“基础概念 + 配置命令 + 七种异常”塞进同一节。确实需要边界说明时，放到本节末尾的“边界”字段或配置折叠区，不要打断主叙事。

## 三、章节结构

每章包含以下字段（详见 `content/rewrite/schema.json`）：

| 字段 | 作用 | 长度建议 |
| --- | --- | --- |
| `intro` | 用一个具体场景把本章问题提出来，承接上一章 | 80–180 字 |
| `why` | 为什么现在学这一章；与已学知识的关系 | 60–150 字 |
| `objectives` | 2–4 条可检查的学习目标，动词开头 | 每条 12–35 字 |
| `outcome` | 学完能做到什么，面向能力而非“了解” | 30–80 字 |
| `recap` | 用一段话把本章主干串起来，不重复细节 | 90–200 字 |
| `bridge` | 下一章要解决的新问题，形成连续学习感 | 30–90 字 |

`intro` 不要写成“本章介绍……”。从一个人、一台设备或一次故障开始。`recap` 不要罗列知识点名称，要说明它们之间的因果关系。

## 四、知识点结构

| 字段 | 作用 | 要求 |
| --- | --- | --- |
| `id` | 稳定编号 | 不得改动 |
| `level` | core / advanced / detail | 必填 |
| `goal` | 本节要解决的一个问题 | 12–40 字，一句话 |
| `lead` | 场景、矛盾或问题，引出本节 | 60–180 字；不要先给定义 |
| `sections` | 2–5 个自然分节 | 每节 `title` + `text`，可含 `steps` |
| `check` | 理解检查 | core 必填；问题 + 答案 + 简短解释 |
| `example` | 已解案例 | 3 步以上，必须提供新信息，不能复述正文 |
| `takeaway` | 一句话核心结论 | 20–60 字 |
| `boundary` | 技术边界/例外 | 可选；没有就省略 |
| `visualCue` | 如果本节有交互/图示，写一句“看什么” | 可选；不要复述图形细节 |

`sections[].text` 用 1–4 个短段落，每段 2–4 句；单节 300–700 字，一个知识点合计 600–1500 字。`sections[].steps` 用于真正有先后顺序的过程；纯概念不要硬拆步骤。

### `example` 与正文的分工

- 正文讲“一般规律”。
- `example` 讲“把规律放到一个具体场景里走一遍”，必须出现正文没有的具体数值、判断或分支。
- 案例要有结果和结论，不能只写“然后配置”。
- 旧稿中 `walkthrough` 与 `process` 完全重复的，必须重写：案例要引入新的条件或反例。

### `check` 的分工

- 检查的是“是否理解因果关系”，不是背定义。
- 问题要能用一个判断或两三句话回答。
- 答案后给一句“为什么”，不要展开成第二篇正文。
- 不设分数、不记录对错。

## 五、语言规范

### 句子与段落

- 一句话讲清一个核心意思。长句拆开，避免一串“的、并、以及、从而”。
- 一段围绕一个问题。段落之间用因果、转折、递进自然连接。
- 先用日常语言解释，再引入正式术语。例：先说“把数据交给离目的地更近的一台设备”，再引出“下一跳”。
- 多写“因为、所以、如果、于是、但是、这意味着”，少写“具有、进行、实现、相关、上述”等文档词。
- 不写“本节将介绍……”“综上所述”“值得注意的是”“不难发现”“众所周知”。
- 不堆砌形容词，不写宣传语，不用“赋能、使能、全方位、极致”等词。
- 避免防御性长句。技术边界集中写，不要每段都加“具体情况以设备为准”。

### 术语

- 首次出现：中文名 + 英文缩写（如果有）+ 它解决的问题。例如：“交换机需要一张表记住‘哪个 MAC 从哪个端口来’，这张表叫 MAC 地址表。”
- 第二次出现可直接用术语。
- 正式定义放入统一术语库；正文不要重复完整定义。
- 不假设缩写可读。OSPF、BGP、VXLAN 等第一次出现必须展开中文含义。
- 同一概念全站用同一名称。不要一会儿“网关”一会儿“默认路由器”。

### 技术与边界

- 保留旧稿中的技术结论、方向、条件、命令与数字。不得为了通顺改变技术事实。
- 不新增未经核实的命令、版本号、性能数字、设备型号限制。
- 讲常见情况在前，例外在后。例外用一小段或“边界”字段说明，不要提前吓退读者。
- 涉及“设备可能不同”时，写清哪一部分是标准、哪一部分依赖实现。
- 配置命令保持原样，放在折叠区；正文只解释“这条命令改变什么、验证什么”，不逐行复述命令。

## 六、图文与交互

- 有拓扑/时序/报文/状态表的节，正文要写出“看哪里、为什么变化”，与图形同步；不要先写一大段文字再附一张无关的图。
- 不要在文字里逐字复述图形已经表达的内容。用图形承担空间关系、消息顺序、字段嵌套，文字承担因果和判断。
- 不是每个知识点都必须配图。没有合适图形时，把过程写清楚即可。
- 有预测组件的节，先让读者形成判断，再看结果；正文不要提前泄露结果。
- 理解检查用折叠答案，不打断阅读；不要做弹窗连环问。

## 七、去重与衔接

- 每个知识点只“拥有”一个主问题。相邻知识点需要同一概念时，用一句“前面已经知道……”带过，不重新定义。
- 章节导语、知识点正文、案例、小结之间不得互相抄写。小结负责建立联系，不重复细节。
- 章与章之间：`why` 说明“上一章解决了什么，这一章还缺什么”；`bridge` 说明“下一章会遇到什么新矛盾”。
- 同一技术在不同章节出现时，只保留一个“主讲解”，其他章节从新角度引用。例如 VLAN 的主讲解在 ICT-004，WLAN 章节只讲无线侧如何映射 VLAN。

## 八、技术准确性检查

每批完成后逐项检查：

1. 方向：源/目的、入/出、请求/响应、发送/接收是否写反。
2. 层次：帧、包、段、报文的使用是否正确。
3. 条件：是否把“通常”写成“一定”，是否漏掉关键前提。
4. 顺序：协议步骤、表项更新时点、状态迁移是否符合原稿与标准。
5. 数字：前缀、端口、定时器、字段长度是否与原稿一致。
6. 命令：是否保留原命令与平台说明，是否把示例当成通用 CLI。
7. 边界：是否把厂商实现写成协议标准，是否把实验假设写成现网事实。

## 九、页面呈现约定

- `core` 正常展示；`advanced` 与 `detail` 显示层次标记，读者可自行决定是否深入。
- 配置、命令说明、故障排查放入页面折叠区，不干扰基础原理阅读。
- 章节开头显示学习目标；章末显示小结与下一章衔接。
- 每个 core 知识点有一个折叠的理解检查；不强制每个知识点都有。
- 进度只记录“本章已学完”，不记录答题、分数或行为轨迹。

## 十、合格线

一篇合格的知识点必须同时满足：

- 开头 3 句内出现具体问题或场景，而不是定义。
- 读完 `lead` 能说出“为什么需要它”。
- `sections` 能回答“它怎么发生”和“为什么这样设计”。
- `example` 能独立复现一个判断，且不与正文重复。
- `check` 能检验因果理解，而不是记忆。
- 全文没有未解释的缩写（除本节之前已解释过的）。
- 技术结论与旧稿一致，没有新增未经核实的具体细节。
- 读起来像一位老师在讲，而不是产品手册在列条目。

## 十一、分批改写与验收流程

全站按知识依赖和领域分为 36 批（`content/rewrite/manifest.json`），每批 1—5 章、最多 13 个知识点。批次只影响写作与审查顺序，不改变考纲章节和编号。

每一批必须经过：

1. `python3 scripts/validate_rewrite.py batch-XX`：字段、长度、覆盖、层次、重复句、案例与正文重复、可视化提示、来源术语保留。
2. 人工抽读至少 2 个知识点：是否先场景后定义、是否解释了“为什么”、案例是否提供新信息、技术方向是否正确。
3. 合并后 `python3 scripts/audit_content.py`：94/322 覆盖、章节目标、全局重复句、近重复段落、过长句/段、模板标题、核心检查、词条覆盖。
4. 全部合并后 `python3 build.py`、`node test-models.cjs`、`node test-teaching.cjs`、`node scripts/render_check.cjs`，并用桌面与窄屏浏览器抽查首页、章节、交互、术语和进度。

发现问题的处理原则：先修正最早的不一致（前置概念、技术方向、层次错位），再润色语言；不通过加长篇幅掩盖结构问题。
